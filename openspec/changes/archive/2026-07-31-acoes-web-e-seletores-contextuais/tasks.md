Os quatro `anyOf` **colapsam numa união** (9 keys), documentada em `LEGENDARY_OPTIONS_PERMISSIONS`. Lista e detalhe de Legendários/Equipes **não** foram afrouxados. `GET /tops/:id/participants/options` confirmado compatível e intocado (§1.5).
- [x] 3.2 Implementar opções de candidatos a membro sob Equipes, se o endpoint global for incompatível — `GET /teams/:id/member-candidates/options`, permission `teams.members.add`. Exclui quem já é membro **ativo** e os inativos. Projeção **id/nome/LGND** (sem cidade nem igreja — aqui a cidade não é dimensão de elegibilidade).
- [x] 3.3 Implementar/reutilizar opções de candidatos a participantes e servos sob TOP — `GET /tops/:id/participant-candidates/options` e `.../servant-candidates/options`, permissions `tops.participants.add` e `tops.servants.add`. Compartilham um `topCandidateOptions` privado porque a elegibilidade é a mesma nos dois sentidos: `addParticipant` e `addServant` **ambos** recusam quem já é participante *ou* servo ativo do TOP — os papéis são mutuamente exclusivos, então os dois seletores excluem os dois conjuntos.
- [x] 3.4 Implementar/reutilizar opções de Equipes candidatas sob TOP — **reutilizado**, não criado: `GET /teams/options` já tinha projeção mínima (id/nome/status) e escopo por `AccessPolicyService`; só faltava a permission. Agora `anyOf('teams.read', 'tops.teams.add', 'tops.teams.update')`. ⚠️ **Achado:** o `top-team-form` **não usava** esse endpoint — usava `GET /teams?perPage=100`, carregando até 100 objetos `Team` completos num `<select>`, contra o non-goal "não carregar coleções completas" e gated por `teams.read`. - [x] 3.5 Implementar opções de candidatos a participantes sob Ações Sociais — `GET /social-actions/:id/participant-candidates/options`, permission `social-actions.participants.add`. Distinto de `volunteers/suggestions`, que é curadoria por interesse/profissão/expertise e segue exigindo `social-actions.read`.
- [x] 3.6 Implementar ou preservar separadamente opções de User e Legendary em Igrejas conforme o campo real — **preservado, nada a implementar** (caso C do inventário). `church-form` tem dois campos de tipos diferentes (`spiritualLeaderUserId` = User, `spiritualLeaderLegendaryId` = Legendary); criar um endpoint contextual de "líder" fundiria os dois tipos, que é justamente o que a spec proíbe.
- [x] 3.7 Validar permission da ação e escopo do recurso-pai em cada endpoint — pai sempre validado **antes** de consultar candidatos, com teste provando que `legendary.findMany` nem é chamado: Equipes via `assertTeamVisible` (403→404) + `findExistingTeam`; TOP via `TopScopeGuard` (já converte fora-de-escopo em 404) + `findExistingTop`; Ações Sociais via `findExisting` (escopo de cidade → 404).
- [x] 3.8 Aplicar busca limitada, ordenação determinística, elegibilidade e projeção mínima sem PII — busca pelo `searchText` **normalizado** (o caminho canônico de `GET /legendarios`, que já agrega nome/cidade/LGND), termo vazio não vira clause (`contains: ''` casaria o diretório inteiro); `take` do DTO (máx. 100); `orderBy: [fullName, id]` — sem o `id` o corte por limite não é estável entre homônimos. **Nenhum endpoint amplia o diretório:** todos aplicam o mesmo `buildLegendaryWhere` do endpoint global, então são subconjunto estrito dele, e escopo vazio segue fail-closed. **Regra de cidade — CORRIGIDA em 31/07 após medir os dados:** a primeira versão herdava a cidade do pai como filtro padrão. Medido no banco de homologação, isso escondia **99 dos 242** candidatos por TOP, sem escape pela interface (o helper `query()` do web descarta string vazia), e ainda transformava a busca pelo nome de quem morava fora em resultado vazio. O Davi confirmou a regra de negócio: **participação em TOP não tem relação com a cidade do Legendário — qualquer um pode ir a qualquer TOP, de qualquer rota.** Hoje `city` é filtro OPCIONAL do cliente, nunca herdado; mesma semântica do `city` de `volunteers/suggestions`. A spec delta foi ajustada junto. Verificado: os dois TOPs passaram de 142/143 para 241/242 candidatos.
- [x] 3.9 Adicionar testes de `403`, `404`, candidatos inelegíveis, pai externo e contrato mínimo — 33 testes novos. Ele roda o guard real sobre o decorator real e prova as duas direções — a ação destrava, e `legendarios.read` (ou a leitura do próprio pai) **não** destrava.
